# 触发器与条件

触发器是 LiDungeon 的“执行入口”，条件是“放行阈值”，动作是“真正行为”。  
这三层分开理解后，副本问题定位会快很多。

## 一、模型

### 1. 触发器（Trigger）
在某个时机触发，例如：
- 玩家进入副本
- 副本倒计时开始/结束
- 特定怪物死亡 / 全体清场
- 玩家进入指定区域

### 2. 条件（Condition）
在触发后判定是否满足：
- 世界/副本 ID 是否匹配
- 当前参与人数
- 权限节点是否满足
- 是否处于指定阶段
- 是否有外部依赖可用

### 3. 动作（Action）
- 发送提示
- 刷怪
- 奖励发放
- 阶段切换
- 副本成功/失败结算

## 二、执行顺序与优先级

```text
事件触发 -> 触发器匹配 -> 条件链校验 -> 动作执行 -> 记录状态
```

- 同一层中尽量使用“最小条件”先过滤（减少无效判断）；
- 对高频事件不要堆叠过深链路，优先拆分；
- 关键动作建议保留“失败兜底”。

## 三、常见配置场景

### 场景 A：副本开始提示
- 触发：副本开始事件
- 条件：玩家数>0 且副本状态为 `PREPARE`
- 动作：广播提示 + 记录开始时间

### 场景 B：阶段 Boss 击杀
- 触发：目标生物死亡
- 条件：当前阶段为 `BOSS_PHASE` 且击杀者为参与者
- 动作：开启下一阶段 / 发放临时奖励 / 播放提示

### 场景 C：失败超时
- 触发：计时到 0
- 条件：当前副本未达成目标
- 动作：结算失败 + 清理实例 + 发送提示

## 四、设计建议（防止“触发少”）

1. 每类逻辑只配一条主链，分支动作做副链；
2. 条件命名清晰：`cond_xxx` / `cond_player_scope` 形式便于查日志；
3. 给每条动作配置写注释（中文）；
4. 先在测试副本验证，再批量复制到主副本；
5. 任意编辑后只改一个方向（条件或动作），避免一次引入两类变量导致回归。

## 五、排障（命令 -> 配置 -> 日志）

### 命令层
- 先确认 `/lidungeon edit <id>` 可进入；
- 检查副本是否实际加载到内存；

### 配置层
- 条件是否闭合（是否缺少“必填字段”）；
- 事件字段与动作参数是否一致；
- 世界 ID / 阶段名是否拼写一致；

### 日志层
- 触发无动作时重点看：是否触发命中、是否被条件拦截、是否动作执行异常；
- 连续失败时，优先看是否存在高频等待（说明状态切换逻辑卡住）。

## 六、多世界注意点

- 世界池应先准备；
- 不建议运行中临时新增世界；
- 如果世界池不稳定，副本通常会在进入阶段表现为“无动作”或“实例未分配”类问题。

## 七、最小调试清单

- 先把“启动事件”与“退出事件”做一条可触发链；
- 再补充“清场事件”；
- 最后补“奖励事件”。  

按这个顺序，定位速度通常是三分之一时间。
