# 安装与更新

## 支持环境

| 服务端 | Java | 说明 |
| --- | --- | --- |
| Paper/Folia 1.21.11 | Java 21 | 插件的最低运行字节码 |
| Paper/Folia 26.2 | Java 25 | 与当前 26.2 服务端保持一致 |

同一个 `LiDungeon-2.0.1-zhcn-folia.8-paper-folia-1.21.11-to-26.2.jar` 可用于上述环境。不要改 Jar 文件名来判断内部版本，应以 `/lidungeon help` 和 `plugin.yml` 为准。

## 可选依赖

LiDungeon 没有强制前置插件。`plugin.yml` 中的公共 Java 库由服务端 libraries 机制在首次启动时下载，不打进插件 Jar。

可选联动包括 MythicMobs、MythicCrucible、MythicQuests、MythicRPG、PlaceholderAPI、Heroes、Citizens、PacketEvents、BetonQuest、Vault、PartyAndFriendsGUI、Parties、Multiverse-Core、Multiverse-Inventories。缺少它们不会阻止基础地牢加载，但对应菜单、条件或功能不会出现。

## 全新安装

1. 停止服务器。
2. 把 LiDungeon Jar 放入 `plugins/`，确保目录中没有旧 MythicDungeons/LiDungeon 重复 Jar。
3. 启动一次，让服务端下载 libraries 并生成默认文件。
4. 检查控制台是否成功加载中文语言、地牢、功能、触发器和条件。
5. 执行 `/lidungeon help`。
6. 停服后修改 `plugins/LiDungeon/config.yml`；Folia 服同时配置预加载世界池。
7. 再次启动并执行[上线验收清单](验证清单.md)。

首次启动需要访问 Maven 仓库下载公共库。若控制台显示 library 下载失败，应先处理网络、代理或仓库访问问题，不要把第三方依赖手工塞进 LiDungeon Jar。

## 从旧 MythicDungeons 迁移

1. 停服并完整备份旧插件目录及世界目录。
2. 保留旧 `maps/`、`globalplayerdata/` 和需要的语言/主配置自定义项。
3. 移除旧 Jar，只放入当前 LiDungeon Jar。
4. 将数据复制到 `plugins/LiDungeon/`，不要同时保留两个插件读取同一份地图。
5. 启动后观察自动配置升级日志。
6. 执行 `/lidungeon reload all` 前先确保没有活动实例；在游戏内若有活动实例，重载需要再次执行确认。
7. 逐个执行 `/lidungeon status <地牢>`、`edit`、`save`、`play` 验收。

内部地图配置键、`dungeons.*` 权限、API 包名和 PAPI 标识 `%md_...%` 为兼容旧地图而保留，不代表对外主命令仍是 `/md`。

## 覆盖更新

更新前至少备份：

```text
plugins/LiDungeon/config.yml
plugins/LiDungeon/lang/
plugins/LiDungeon/maps/
plugins/LiDungeon/globalplayerdata/
plugins/LiDungeon/backups/
```

推荐流程：

1. 通知玩家退出全部地牢。
2. 使用 `/lidungeon status` 确认没有活动实例和编辑会话。
3. 正常停服。
4. 备份数据目录和旧 Jar。
5. 替换 Jar，不要删除现有配置。
6. 启动并检查配置补缺日志。
7. 先验证一个测试地牢，再开放正式地牢。

配置迁移会补充缺失项和注释，不应覆盖已有值、自定义消息或额外节点。出现“配置版本过旧，正在更新”是迁移提示；出现“更新完成”只代表配置结构完成，不代表地图、世界池和触发链都已验收。

## 重载的区别

| 命令 | 实际作用 |
| --- | --- |
| `/lidungeon reload` | 重载全局主配置和语言等配置 |
| `/lidungeon reload <地牢>` | 重载一个地牢定义 |
| `/lidungeon reload all` | 重载所有地牢定义 |

地牢有活动实例时，游戏内执行者需要再次执行相同命令确认。控制台执行不会经过游戏内二次确认，因此生产服更应先确认无玩家。

世界池名单、服务端世界加载顺序、可选插件增删和底层 libraries 变更建议完整重启，不依赖热重载。

## 更新失败时回滚

1. 立即停止服务器，避免新版本继续写数据。
2. 保存本次失败启动的完整日志。
3. 恢复旧 Jar 与同一时间点的数据目录备份。
4. 启动后只开放测试账号。
5. 核对完成记录、冷却、地牢配置和地图方块。

不要只回滚 Jar 而保留已经被新版本迁移的数据；正确回滚必须保证程序与数据来自同一个备份时间点。
